## 2. 指标分层

```text
业务价值：有效看护闭环
    ↓
用户行为：激活、查看、确认、处理、反馈
    ↓
产品链路：感知、判断、告警、响应、沉淀
    ↓
AI质量：Precision、Recall、F1、误告警、延迟
    ↓
工程基础：在线、上报、送达、回执、稳定性
```

| 层级 | 核心问题 |
|---|---|
| 北极星 | 系统是否真正帮助家庭完成有效看护闭环 |
| 激活 | 用户是否完成从注册到首次有效看护 |
| 看护闭环 | 事件是否被发现、送达、处理并沉淀 |
| 告警质量 | 告警是否及时、真实、不过度打扰 |
| AI质量 | 三类场景和生成式AI是否可信 |
| 设备稳定性 | 数据、连接、指令与回执是否可靠 |
| 安全护栏 | 主指标提升是否以漏报、误报或隐私风险为代价 |

## 3. 北极星指标

### 3.1 主指标：有效看护闭环完成率

**业务问题**：对于系统已经生成、且确实需要照护者处理的有效事件，有多少完成了送达、确认、处理和沉淀？

```text
有效看护闭环完成率
= 完成送达、确认/处理及结果记录的有效需处理事件数
÷ 经人工或测试真值确认的有效需处理事件总数
```

#### 事件进入分母的条件

- 事件属于T0.1纳入范围的哭闹L2/L3或危险动作L3。
- 数据质量有效或符合已定义的降级规则。
- 经受控测试真值、人工复核或用户反馈确认是真实事件。
- 同一持续事件按事件合并规则去重。

#### 完成闭环的条件

- 告警获得渠道送达回执。
- 用户完成查看和确认，或系统按规则升级并由授权联系人确认。
- 存在处理结果：已处理、误报、无法判断或无需处理。
- 事件进入时间线/报告数据源并可通过`event_id`追溯。

#### 重要限制

线上闭环率只能衡量已被系统发现的事件，不能自动发现漏报。必须同时观察危险动作Recall、漏报率和受控测试集结果，否则系统少报事件也可能获得虚高闭环率。

| 字段 | 定义 |
|---|---|
| 统计对象 | 去重后的需处理事件 |
| 时间窗口 | 日监控、周复盘 |
| 当前基线 | 【待采集】 |
| T0.1目标 | 首轮受控测试后联合确认，不在无基线时虚构 |
| 护栏指标 | 危险动作Recall、单位时间误告警、告警送达率、设备在线率 |

### 3.2 辅助价值指标

| 指标 | 公式 | 用途 |
|---|---|---|
| 周有效看护家庭数 | 一周内至少完成1次有效看护闭环的去重家庭数 | 观察价值覆盖规模 |
| 有效看护时长 | 数据质量有效且设备在线的看护分钟数 | 区分打开页面与真实看护 |
| 闭环事件数 | 完成闭环的去重事件数 | 观察T0.1工程产出，不单独代表用户价值 |

## 4. 激活漏斗

### 4.1 激活定义

用户完成“设备首次在线＋首次有效数据上报＋首次进入有效看护状态”后，视为完成基础激活；首次处理告警或查看有效报告作为价值激活，不强迫用户等待异常发生。

```text
注册成功
→ 创建/加入家庭
→ 添加宝宝
→ 设备绑定成功
→ 设备首次在线
→ 首次有效数据上报
→ 首次有效看护
→ 首次价值行为
```

### 4.2 漏斗指标

| 编号 | 指标 | 公式 | 当前基线 |
|---|---|---|---|
| ACT-01 | 家庭创建率 | 创建/加入家庭用户数÷注册成功用户数 | 待采集 |
| ACT-02 | 宝宝档案完成率 | 添加宝宝用户数÷创建/加入家庭用户数 | 待采集 |
| ACT-03 | 设备绑定成功率 | 成功绑定尝试数÷有效绑定尝试数 | 待采集 |
| ACT-04 | 首次上线率 | 绑定后规定时间内首次在线设备数÷绑定成功设备数 | 待采集 |
| ACT-05 | 首次有效上报率 | 首次上线后产生有效数据设备数÷首次在线设备数 | 待采集 |
| ACT-06 | 基础激活率 | 完成首次有效看护家庭数÷设备绑定成功家庭数 | 待采集 |
| ACT-07 | 价值激活率 | 完成首次告警处理或有效报告查看家庭数÷基础激活家庭数 | 待采集 |

失败原因必须分组统计：权限拒绝、SN错误、设备占用、配网失败、设备不上线、传感器无数据、后端错误和用户主动退出。

## 5. 看护闭环指标

```text
有效感知 → 场景候选 → 事件成立 → 告警生成
→ 发送 → 送达 → 查看 → 确认/升级 → 处理 → 关闭 → 沉淀
```

| 编号 | 指标 | 公式/口径 |
|---|---|---|
| CLS-01 | 有效感知率 | 有效数据包数÷收到的数据包总数 |
| CLS-02 | 事件生成成功率 | 成功持久化事件数÷满足规则的事件数 |
| CLS-03 | 告警生成成功率 | 成功生成告警数÷应生成告警事件数 |
| CLS-04 | 告警发送成功率 | 渠道接受发送数÷告警发送请求数 |
| CLS-05 | 告警送达率 | 获得送达回执告警数÷发送成功告警数 |
| CLS-06 | 告警查看率 | 用户查看告警数÷已送达告警数 |
| CLS-07 | 告警确认率 | 获得明确确认告警数÷已送达需确认告警数 |
| CLS-08 | 处理完成率 | 有处理结果事件数÷已确认真实事件数 |
| CLS-09 | 超时升级率 | 超时升级事件数÷需确认L2/L3事件数 |
| CLS-10 | 结果沉淀率 | 进入时间线/报告数据源事件数÷已关闭事件数 |

### 5.1 链路延迟

| 指标 | 起点 | 终点 |
|---|---|---|
| 采集上传延迟 | 设备采集时间 | 服务端接收时间 |
| 判断延迟 | 服务端接收有效数据 | 场景/事件判断完成 |
| 告警处理延迟 | 事件成立 | 告警发送请求 |
| 渠道送达延迟 | 告警发送请求 | 渠道送达回执 |
| 端到端告警延迟 | 事件成立 | 渠道送达回执 |
| 用户确认时长 | 渠道送达 | 首位授权用户确认 |

延迟同时报告P50、P95、P99和样本量，不用平均值掩盖长尾。

## 6. 告警质量指标

| 编号 | 指标 | 定义 |
|---|---|---|
| ALT-01 | 告警Precision | 经真值确认的真实告警数÷全部已评估告警数 |
| ALT-02 | 事件Recall | 被系统检出的真实事件数÷受控测试中的全部真实事件数 |
| ALT-03 | 漏报率 | 1－事件Recall |
| ALT-04 | F1 | 2×Precision×Recall÷（Precision＋Recall） |
| ALT-05 | 单位时间误告警 | 误告警数÷有效看护设备小时数 |
| ALT-06 | 重复告警率 | 同一事件重复产生的告警数÷全部告警数 |
| ALT-07 | 误报反馈率 | 用户标记误报告警数÷用户已反馈告警数 |
| ALT-08 | 通知关闭率 | 关闭相关通知家庭数÷收到告警家庭数 |

### 6.1 告警真值来源

真值来源按可信度排序：受控测试预设事件、双人复核标注、照护者现场确认、事后单人反馈。不同来源不可无区别混算；“用户未处理”不等于误报，“用户点击关闭”不等于事件解除。

## 7. 三类核心场景指标

以下均为【复盘方案】中的T0.1受控测试建议门槛，不是行业标准或当前成果。

| 场景 | Precision | Recall | F1 | 漏报率 | 产品侧约束 |
|---|---:|---:|---:|---:|---|
| 熟睡 | ≥90% | ≥90% | ≥90% | ≤10% | 错误状态切换≤1次/小时 |
| 哭闹 | ≥85% | ≥90% | ≥87% | ≤10% | 非哭闹误告警≤1次/8小时/设备 |
| 危险动作 | ≥80% | ≥95% | ≥87% | ≤5% | 非危险误告警≤1次/24小时/设备 |

### 7.1 熟睡专项

- 事件级Precision、Recall和F1。
- 每小时错误状态切换次数。
- 睡眠开始/结束时间误差和总时长误差。
- 数据不足时错误输出“熟睡”的次数。

### 7.2 哭闹专项

- 哭闹事件级Precision、Recall和F1。
- 有效事件P95发现时间≤10秒，起点为满足持续判断条件后。
- 非哭闹误告警次数及环境噪声切片表现。
- 同一哭闹事件重复提醒次数和通知关闭率。

### 7.3 危险动作专项

- 身体越界、攀爬护栏等子场景分别统计，不只报告大类总数。
- 事件级Recall优先，漏报必须逐例复盘。
- 事件成立后L3告警P95送达时间≤3秒。
- 夜间、遮挡、成人抱起、正常站立等困难负样本单独报告。
- 疑似呼吸异常单独立项，不直接套用视觉危险动作指标。

## 8. AI质量指标

### 8.1 模型与规则层

| 指标 | 说明 |
|---|---|
| 分标签Precision/Recall/F1 | 分别评估睡眠、姿态、动作、声音、风险等输出 |
| 场景混淆矩阵 | 显示真实类别被判断成哪些类别 |
| 低置信度率 | 输出“不确定”的样本数÷全部有效样本数 |
| 校准误差 | 检查模型分数能否代表真实正确概率 |
| 数据质量切片 | 白天、夜间、遮挡、噪声、设备型号和月龄分别统计 |
| 模型/规则漂移 | 线上分布或效果相对基线的变化 |

【口头信息｜待材料核验】原项目产品经理表示九类VL模型各类别识别结果均在90%以上。该信息进入指标台账，但在取得模型版本、测试集、逐类口径和报告前，不登记为已核验基线。

| 报告生成成功率 | 成功生成报告数÷有效生成请求数 |

### 8.3 AI陪伴

AI陪伴为P2，不进入T0.1北极星指标。后续监控：唤醒成功率、ASR低置信度率、对话成功率、首响应P95、TTS生成成功率、播放中断率、安全拦截率和外部服务失败率。

### 10.2 命名与数据规则

- 事件名使用小写蛇形命名，采用“对象_动作_结果”结构。
- 枚举值固定，不使用自然语言自由填写关键状态。
- P0事件由服务端或硬件产生，客户端仅补充曝光和操作行为。
- 每条事件定义唯一去重键；补发事件保留原始发生时间。
- 测试、演示和生产数据通过`environment`字段隔离。
- 禁止在埋点中直接上传儿童姓名、原始视频、音频文本或家庭联系方式。

线上埋点中的`labels/scores`仅保存最小必要的结构化结果；原始图像、音频和特征存储另行授权和管理。

## 12. 数据来源与事实表关系

| 数据源 | 主要数据 | 可信用途 |
|---|---|---|
| 客户端埋点 | 页面曝光、点击、授权和用户操作 | 用户行为，不证明后端或硬件成功 |
| 后端业务库 | 绑定、事件、告警、确认、处理、报告 | 业务状态和闭环 |
| 设备日志 | 心跳、采集、执行、错误 | 在线、上报、硬件执行 |
| 模型/规则日志 | 输入摘要、输出、版本、延迟 | AI评估和错误分析 |
| 消息渠道回执 | 发送、送达、失败 | 告警送达事实 |
| 标注测试集 | 场景真值与环境切片 | Precision、Recall、F1、漏报 |

推荐以`event_id`作为看护闭环主键，关联`alert_id`和`command_id`。用户点击日志不可替代消息送达回执，API 200不可替代设备执行回执。

## 13. 数据看板与告警

### 13.1 T0.1看板

1. 激活漏斗：绑定、上线、有效上报、首次看护。
2. 看护闭环：事件、发送、送达、确认、处理、沉淀。
3. 场景质量：三类场景Precision、Recall、F1、误告警和延迟。
4. 设备健康：在线率、有效上报率、重连、回执和错误码。
5. 数据质量：迟到、缺失、重复、时间漂移和版本分布。

### 13.2 异常行动

| 异常 | 处理动作 |
|---|---|
| 危险Recall下降 | 暂停扩大范围，复盘漏报样本、版本和环境切片 |
| 误告警升高 | 检查阈值、困难负样本、去重和时序规则 |
| 送达率下降 | 检查渠道、权限、token、重试和备用联系人 |
| 数据有效率下降 | 按设备/固件/传感器定位并启动降级提示 |
| 回执率下降 | 检查设备在线、协议、指令幂等和超时配置 |
| 报告纠错率升高 | 回溯结构化输入、提示词、模型版本和引用链 |

正式告警阈值应在建立基线后确定；当前文档不虚构监控阈值。

## 14. 数据质量与隐私

### 14.1 数据质量校验

- 完整性：P0字段缺失率、链路ID覆盖率。
- 唯一性：事件、告警和指令重复率。
- 一致性：客户端、后端、设备和渠道状态是否匹配。
- 及时性：迟到、补传和时间漂移比例。
- 合法性：枚举、单位、取值范围和版本字段。
- 可追溯性：指标是否可回溯到原始记录和计算版本。

### 14.2 隐私规则

- 标识符使用内部ID，分析层按需要进一步匿名化。
- 原始视频、音频与结构化埋点分开授权、存储和控制访问。
- 不在通用埋点中记录姓名、电话号码、住址和原始对话文本。
- 外部AI调用需记录数据类别、授权状态、服务方和删除策略。
- 支持按家庭/宝宝撤回授权和删除数据，并保留合规审计记录。

## 15. 验收清单与当前缺口

| 验收项 | 通过条件 |
|---|---|
| 指标可计算 | 分子、分母、去重、排除和时间窗口完整 |
| P0链路可追踪 | `trace_id/event_id/alert_id/command_id`关联完整 |
| 事件状态一致 | 创建、发送、送达、确认、处理和关闭无非法跳转 |

| 硬件结果可信 | 执行成功来自设备回执而非接口返回 |
| 隐私合规 | 最小采集、授权、脱敏、访问和删除机制明确 |

### 15.1 尚待补齐

- 【待采集】真实激活、闭环、告警和设备基线。
- 【待核验】九类VL模型的逐类评估报告和数据集信息。
- 【待实现/核验】真实消息送达回执、统一链路ID和硬件终态回执。
- 【待验证】三类场景事件定义、标注集、阈值及受控测试结果。
- 【待评审】儿童敏感数据、外部AI和保存删除策略。

## 16. 阶段结论

T0.1的数据体系不能只统计页面访问或模型“准确率”。应以有效看护闭环为价值主线，以事件Recall和单位时间误告警为质量护栏，通过统一链路ID贯通感知、判断、告警、响应和沉淀。

当前项目具备较多业务对象和接口结构，但尚未发现完整的数据看板与正式基线。因此本方案中的目标均作为验证门槛或待评审建议，后续必须用真实埋点、受控测试和设备回执形成可审计结果。
