## 2. 背景与问题定义

### 2.1 用户问题

【原始规划】项目主要针对以下家庭看护问题：

1. 主要照护者无法全天持续观察婴幼儿状态，存在安全焦虑。
2. 普通家庭摄像头主要解决“看见”，无法稳定完成状态判断、风险分级和主动提醒。
3. 哭闹、趴睡、翻越护栏等事件发生后，告警、响应和处理结果未形成连续闭环。
4. 睡眠、哭闹、活动和成长里程碑分散，难以形成长期记录。
5. 多名家庭成员共同照护时，需要统一的设备、权限、提醒和事件记录入口。

【待验证】当前项目目录中未发现完整的用户访谈记录、问卷样本、可用性测试或付费验证数据。以上内容应视为产品假设，而不是已经完成市场验证的结论。

### 2.2 产品机会

【复盘方案】智能婴儿床的潜在差异化不只是增加传感器，而是将以下五个环节连接起来：

```text
多模态感知 → 状态与风险判断 → 分级告警 → 人机协同响应 → 成长数据沉淀
```

如果系统只完成摄像、数据展示或单次提醒，就仍然是功能集合；只有事件被发现、通知、处理、记录并用于后续优化，才构成可验证的看护闭环。

## 3. 产品定位与阶段目标

### 3.1 产品定位

面向0—4岁婴幼儿家庭，以婴儿床为硬件载体，通过摄像头、毫米波雷达、麦克风等多模态输入，连接小程序、云端服务和本地交互设备，提供安全看护、异常告警、场景响应、成长记录与AI陪伴能力。

### 3.2 T0阶段目标

【原始规划】T0提出九类场景、端到端响应、识别准确率、连续运行、语音交互和本地数据安全等目标。

【T0事实】现有工程更适合定义为“产品框架和关键链路工程验证”：

- 小程序、后端接口、数据库模型和硬件接入结构已形成。
- 传感器数据上传及五类阈值状态判断存在代码证据。
- 事件查询、确认、成长报告和设备响应接口已形成部分链路。
- 九类多模态分类仍存在随机模拟，不能证明准确率目标已经实现。
- 真实推送送达、硬件执行回执、24小时稳定性及医学安全阈值尚未形成正式验证报告。

### 3.3 T0.1目标

【复盘方案】T0.1不直接追求九类场景全面上线，而是优先完成“熟睡、哭闹、危险动作”三类高价值场景的可验证闭环：

| 目标编号 | 目标 | 判定方式 |
|---|---|---|
| OBJ-T01-01 | 跑通设备绑定、在线、感知数据上传和数据质量判断 | 接口日志、设备状态、数据库记录一致 |
| OBJ-T01-02 | 跑通熟睡、哭闹、危险动作三类规则判断 | 有版本化规则、测试样本和事件记录 |
| OBJ-T01-03 | 跑通事件生成、分级告警、用户确认和超时升级 | 推送回执、确认记录和升级记录可追踪 |
| OBJ-T01-04 | 跑通安全范围内的场景响应及执行回执 | 指令、硬件回执和失败降级记录一致 |
| OBJ-T01-05 | 将事件和处理结果沉淀至时间线及成长报告 | 报告内容可回溯至原始事件 |
| OBJ-T01-06 | 建立从规则原型转向多模态算法验证的数据基础 | 数据字典、标注规范、样本集和评估报告齐备 |

### 3.4 成功原则

- 安全优先：宁可提示人工确认，也不输出无依据的确定性结论。
- 闭环优先：先验证发现、通知、处理和记录，再扩展场景数量。
- 证据优先：目标值、实现状态和实测结果分别记录。
- 人机协同：AI提供辅助判断，不替代监护人和医疗专业人员。

## 4. 用户、角色与权限

| 角色 | 核心任务 | 主要权限 |
|---|---|---|
| 设备管理员 | 绑定设备、创建家庭、配置规则与成员 | 设备及家庭全部管理权限 |
| 主要照护者 | 查看状态、接收告警、确认和处理事件 | 看护、告警处理、报告查看权限 |
| 协同照护者 | 在授权范围内协助看护 | 被授权设备、宝宝和告警权限 |
| 研发/测试人员 | 配置测试环境、查看日志、执行场景测试 | 测试环境调试和审计权限 |
| 婴幼儿 | 被动接受看护和经家长授权的场景响应 | 不承担操作和决策责任 |

### 4.1 权限原则

- 视频、音频、生理信号和儿童成长数据按敏感数据管理。
- 新家庭成员必须由设备管理员授权。
- 告警确认、规则调整、视频查看和数据导出必须记录操作者与时间。
- 权限撤销后，用户不得继续访问实时画面和历史敏感数据。
- 测试人员原则上只能访问脱敏数据或明确授权的测试数据。

## 5. 核心用户场景与端到端旅程

### 5.1 正常看护旅程

```text
绑定设备 → 完成授权 → 设备在线 → 采集有效数据
→ 判断当前状态 → 家长查看 → 状态进入时间线 → 形成报告
```

### 5.2 异常看护旅程

```text
检测疑似异常 → 校验数据质量 → 形成事件与风险等级
→ 通知照护者 → 用户查看并确认 → 执行人工或设备响应
→ 记录处理结果 → 事件关闭 → 进入报告与规则复盘
```

## 6. 九大场景蓝图与版本范围

### 6.1 九大场景

【原始规划】原始材料定义了九类被动看护场景：熟睡、侧睡/趴睡、刚睡醒、坐起、翻身、站立、高兴玩耍、哭闹和危险动作。

【重要边界】九类场景是产品场景集合，不等同于九分类算法已经完成。T0主后端存在五类阈值状态判断，多模态融合和场景分类仍有模拟结果。

### 6.2 场景版本规划

| 场景 | T0材料状态 | T0.1范围 | 后续方向 |
|---|---|---|---|
| 熟睡 | 有候选生理、动作和声音规则 | P0闭环验证 | 个体化睡眠基线 |
| 哭闹 | 有三级分贝及辅助信号规则 | P0闭环验证 | 哭声类型和原因辅助判断 |
| 危险动作 | 有呼吸、护栏、身体越界等子场景 | P0，先选可测试子场景 | 多模态风险融合 |
| 侧睡/趴睡 | 有持续时间候选规则 | P1规则验证 | 姿态模型优化 |
| 刚睡醒 | 有动作、表情和声音描述 | P1 | 状态转换识别 |
| 坐起 | 有角度和持续时间候选值 | P1 | 月龄适配 |
| 翻身 | 有动作里程碑描述 | P1 | 动作完成度评估 |
| 站立 | 同时涉及成长与安全 | P1 | 根据位置和月龄区分风险 |
| 高兴玩耍 | 有表情、声音及动作描述 | P2 | 情绪和互动质量分析 |

### 6.3 T0.1不做范围

- 不验收完整九分类多模态模型。
- 不提供疾病诊断、窒息诊断或医疗处置建议。
- 不允许生成式AI直接决定L3紧急告警是否成立。
- 不宣称完成量产级硬件、安全、隐私或医疗认证。
- 不在当前版本验证支付、商业化、供应链和售后体系。
- AI陪伴不进入安全看护的关键决策链。
- 未经安全评审，不自动执行高音量、强闪光或可能影响婴幼儿的刺激性动作。

## 8. T0.1产品方案

### 8.0 核心看护闭环

![T0.1核心看护闭环](assets/diagrams/02-care-closed-loop.png)

[可编辑Mermaid源文件](assets/diagrams/02-care-closed-loop.mmd)

闭环中任何一步失败都必须产生明确状态：数据不可用时不输出确定性场景，低置信度进入观察或复核，告警未确认进入升级，硬件无回执进入重试或人工接管，误报反馈进入样本复核而不是直接修改真值。

### 8.1 感知层

系统应记录每类输入的设备ID、宝宝ID、采集时间、上传时间、单位、数据质量和来源。

| 输入 | 主要用途 | T0.1要求 |
|---|---|---|
| 毫米波雷达 | 呼吸、心率、活动度 | 明确单位、采样频率、缺失值和异常值范围 |
| 摄像头 | 姿态、位置、动作、人工查看 | 明确授权、画面可用性、遮挡和夜间条件 |
| 麦克风 | 声音强度、哭声与环境声音 | 明确分贝校准、噪声条件和隐私策略 |
| 设备状态 | 在线、电量、网络及执行能力 | 所有事件必须关联当时设备状态 |

#### 数据质量状态

- 有效：输入字段完整且处于可用范围，可进入规则判断。
- 降级：部分传感器缺失，只允许执行明确支持单传感器的规则。
- 无效：关键数据缺失、过期或冲突，不生成确定性场景结论。
- 离线：设备超过约定时间无心跳，停止展示“实时”状态并提醒照护者。

### 8.2 判断层

T0.1采用“确定性规则＋人工确认”的验证方式，多模态模型作为后续能力。

每条规则必须包含：

- 场景及规则版本。
- 输入字段、单位和数据来源。
- 适用月龄与前置条件。
- AND/OR组合逻辑。
- 触发阈值、持续时间和置信度。
- 退出阈值、迟滞区间和冷却时间。
- 数据缺失、冲突和低置信度处理。
- 告警等级及可执行响应。
- 阈值依据、负责人和验证状态。

《被动式功能设计t0》中的数值统一标记为“候选阈值”，在完成设备标定、样本测试和安全评审前不得写成已验证标准。

### 8.3 告警层

| 等级 | 定义 | 示例 | 通知及处理 |
|---|---|---|---|
| L1提醒 | 需要了解但无需立即介入 | 刚睡醒、轻度哭闹 | App普通消息，可进入汇总 |
| L2关注 | 可能需要照护者及时查看 | 持续哭闹、持续异常姿态 | App强提醒，要求查看或确认 |
| L3紧急 | 疑似高风险，需要立即人工介入 | 身体越过护栏、持续危险动作 | 强提醒、多联系人升级、持续至确认 |

告警必须支持：

- 同一事件去重，避免短时间重复轰炸。
- 告警创建、发送、送达、查看、确认、处理和关闭状态。
- L2/L3超时未确认时升级至备用联系人。
- 用户可标记“真实事件、误报、无法判断”。
- 发送失败进入重试或备用渠道，并记录失败原因。
- 设备离线、数据无效和疑似异常必须使用不同文案。

### 8.4 响应层

| 响应类型 | 使用边界 | 回执要求 |
|---|---|---|
| App提示 | 展示事件、依据及处理建议 | 记录送达、查看和操作 |
| 灯光/屏幕 | 仅使用通过婴幼儿安全评审的低刺激方案 | 记录指令、执行、失败和结束 |
| 语音/亲子音频 | 由家长预先授权和配置 | 记录音频来源、音量、时长和中止 |
| 人工处理 | L2/L3核心响应方式 | 记录确认人、时间和处理结果 |

高风险场景不得仅以自动安抚作为处理完成。若硬件无回执，系统应提示“响应未确认执行”，不得显示执行成功。

### 8.5 成长沉淀

系统将状态片段、事件、照护者反馈和处理结果沉淀为：

- 日/周状态时间线。
- 睡眠时长和睡眠片段。
- 哭闹次数、持续时间及家长反馈。
- 成长里程碑和温馨瞬间。
- 设备离线及数据质量记录。
- 周报或月报摘要。

AI生成报告必须引用结构化事件，不得凭空生成健康结论；外部AI服务失败时提供规则化摘要并标记生成方式。

## 9. 三类核心场景需求

### 9.1 熟睡场景

**用户价值**：让照护者了解宝宝是否处于稳定睡眠状态，同时验证正常状态的数据闭环。

**候选输入**：呼吸率、心率、身体位移、活动度、环境声音和姿态。

**原始候选值**：材料中出现呼吸12—20次/分、动作位移小于5厘米、持续10分钟或30分钟、声音小于30dB等条件。

**产品要求**：

- T0.1必须先统一持续时间及组合逻辑。
- 熟睡是状态判断，原则上不发送持续性告警。
- 数据不足时显示“状态判断中”或“数据不足”，不得默认显示熟睡。
- 状态变化应进入时间线，但需通过合并策略避免生成大量碎片。
- 候选生理阈值仅用于受控验证，需注明设备误差和适用范围。

### 9.2 哭闹场景

**用户价值**：帮助照护者及时发现并区分轻度、持续和疑似高风险哭闹。

**原始候选规则**：

| 等级 | 候选条件 |
|---|---|
| L1 | 声音40—55dB，生命体征相对稳定，并有轻微皱眉等辅助信号 |
| L2 | 声音55—70dB并伴随动作，持续30秒后可触发家长预设音频 |
| L3 | 声音高于75dB并伴随心率明显变化、呼吸急促或剧烈动作 |

**产品要求**：

- 分贝阈值必须经过麦克风距离、环境噪声和设备校准测试。
- 表情、动作和生理信号在规则中是必要条件还是辅助条件必须明确。
- L2自动播放音频前必须获得家长授权，并支持立即中止。
- L3不得仅由单一声音阈值触发确定性危险结论，应提示人工查看。
- 告警关闭时收集家长反馈，作为规则评估标签。

### 9.3 危险动作场景

**用户价值**：尽快发现可能造成跌落、翻越或呼吸风险的事件，并促使照护者人工介入。

**候选子场景**：靠近床沿并翻滚、攀爬护栏、身体越界、异常站立及疑似呼吸异常。

**产品要求**：

- T0.1优先选择可重复测试、风险边界明确的“靠近床沿/身体越界”子场景。
- 每个子场景单独定义数据、阈值、优先级和验收用例，不合并为模糊的“危险”。
- 原始材料中“距离安全区20厘米、翻滚角度大于90度、头部或上半身投影越过护栏”等仅作为候选规则。
- 疑似呼吸异常涉及医疗安全，心率低于40或50等冲突数值不得直接进入产品标准。
- L3事件必须保留触发快照、关键数据、规则版本和人工处理结果。

## 11. AI策略与数据闭环

### 11.1 AI能力拆分

| 能力 | T0状态 | T0.1策略 | 后续评估 |
|---|---|---|---|
| 生理与活动状态 | 阈值规则 | 规则版本化和测试 | 异常值率、规则命中质量 |
| 姿态与动作识别 | 有规划及部分接口 | 受控样本验证 | Precision、Recall、混淆矩阵 |
| 哭声识别 | 有声音规则和服务结构 | 分贝规则＋人工反馈 | 误报率、漏报率、噪声鲁棒性 |
| 多模态融合 | 场景分类含模拟 | 不作为已上线能力 | 分场景评估、缺失模态表现 |
| 成长报告生成 | 外部LLM＋兜底链路 | 限定输入和输出边界 | 事实一致性、采用率、投诉率 |
| AI语音陪伴 | 迁移原型 | 不进入P0范围 | 成功率、延迟、主观体验 |

### 11.2 数据闭环

```text
原始信号/特征 → 规则或模型版本 → 场景结果 → 告警
→ 用户确认与处理 → 真实/误报/不确定标签 → 规则复盘与模型评估
```

训练或评估数据必须记录来源、授权、采集环境、设备型号、月龄区间、标注者和版本；训练集、验证集和测试集应按宝宝或家庭维度隔离，避免同一对象数据泄漏造成虚高结果。

### 12.1 三类核心场景的事件级验证目标

以下目标用于T0.1受控测试，属于产品与工程联合评审的起始门槛，不是行业通用标准、医学安全标准或T0已达成果。完成首轮基线测试后，产品、算法、硬件、测试及安全相关人员应根据样本分布、设备误差和误报/漏报成本共同调整。

| 核心场景 | Precision | Recall | F1 | 漏报率 | 产品侧误报约束 |
|---|---:|---:|---:|---:|---:|
| 熟睡 | ≥90% | ≥90% | ≥90% | ≤10% | 错误状态切换≤1次/小时 |
| 哭闹 | ≥85% | ≥90% | ≥87% | ≤10% | 非哭闹误告警≤1次/8小时 |
| 危险动作 | ≥80% | ≥95% | ≥87% | ≤5% | 非危险误告警≤1次/24小时 |

#### 熟睡补充指标

- 状态判断应采用连续有效数据窗口，不能以单帧结果确认熟睡。
- 记录睡眠开始/结束时间误差、睡眠总时长误差和每小时错误状态切换次数。
- 数据不足、传感器离线或信号冲突时，不得默认输出“熟睡”。

#### 哭闹补充指标

- 有效哭闹事件P95发现时间建议≤10秒。
- 发现时间从满足预设持续判断条件后开始计算，不将去噪观察窗口混入系统处理延迟。
- 同时统计每设备每8小时非哭闹误告警次数，防止告警疲劳。

#### 危险动作补充指标

- 满足规则触发条件后，L3告警端到端P95送达时间≤3秒。
- “危险动作”必须拆分为靠近床沿、身体越界、攀爬护栏、危险站立等独立子场景分别测试。
- 疑似呼吸异常涉及医学安全和传感器测量能力，不直接套用本表目标，必须单独接受专业与硬件评审。

### 12.2 指标定义与关系

- `Precision = 正确识别的目标事件数 ÷ 系统识别为该场景的全部事件数`，用于衡量系统告警中有多少是真的。
- `Recall = 正确识别的目标事件数 ÷ 真实发生的该场景事件总数`，用于衡量真实事件中有多少被发现。
- `F1 = 2 × Precision × Recall ÷（Precision + Recall）`，用于综合观察Precision和Recall的平衡。
- `漏报率 = 1 - Recall`，因此漏报率与Recall不是两项互相独立的指标。
- 严格意义的误报率FPR不等于`1 - Precision`；面向产品体验还应统计单位时间误告警次数。

### 12.3 测试与统计口径

- 以完整事件为主要统计单位，不以单帧准确率作为主要发布依据。
- 同一连续事件只计算一次；事件开始、结束、合并和重复告警规则应提前冻结。
- 准确率不能替代Precision、Recall、F1和分场景混淆矩阵。
- 安全场景优先关注漏报，并同时监控误报造成的告警疲劳。
- 端到端延迟从设备事件时间开始，到用户渠道确认送达结束。
- 测试集按宝宝或家庭维度与训练集、验证集隔离，避免同一对象数据泄漏造成指标虚高。
- 测试环境至少覆盖白天、夜间、遮挡、环境噪声、不同网络条件和传感器缺失。
- 每个核心场景首轮建议准备不少于100个独立正样本事件，并配置足够的正常及相似负样本；样本不足时必须披露，不把结果外推为真实家庭表现。
- 危险动作使用假人、模拟装置、授权历史数据或其他安全受控方式采集，不得为了测试让真实婴幼儿执行危险动作。
- 所有指标需同时记录样本量、类别分布、置信区间、测试环境、规则/模型版本及时间范围。
- 生理与安全阈值必须经过专业及硬件验证，产品目标不能替代医学标准。

## 13. 异常、降级与人工接管

| 异常 | 系统行为 | 用户提示 |
|---|---|---|
| 设备离线 | 停止输出实时结论，记录离线事件 | “设备已离线，当前状态不可用” |
| 网络不稳定 | 本地缓存允许的数据，恢复后补传 | 展示最后更新时间及同步状态 |
| 单传感器失效 | 进入支持该缺失模态的降级规则 | “部分传感器不可用，判断能力下降” |
| 多传感器冲突 | 不输出确定性安全结论，要求人工查看 | “检测结果存在冲突，请查看实时状态” |
| AI低置信度 | 标记疑似事件，不执行高风险自动动作 | “疑似异常，请人工确认” |
| 告警发送失败 | 自动重试并尝试备用渠道 | 事后展示失败与补发记录 |
| 硬件无回执 | 标记执行未确认，不展示成功 | “设备响应未确认，请人工处理” |
| L3超时未确认 | 升级备用联系人并持续记录 | “紧急事件尚未确认” |
| 权限不足 | 阻止访问并记录审计日志 | “当前账号无此权限” |
| 云端AI不可用 | 使用规则化摘要或关闭非关键AI能力 | 不影响P0安全告警链路 |

## 14. 非功能需求

### 14.1 稳定性

- P0服务异常不得导致原始事件和用户处理记录丢失。
- 设备、服务和消息渠道应具有可观测状态。
- T0.1至少完成一次24小时连续运行测试并形成正式报告。

### 14.2 性能

- 对L3事件分别记录感知、判断、入库、发送、送达各阶段耗时。
- 页面不得使用未更新时间戳的缓存数据冒充实时状态。

### 14.3 安全与隐私

- 敏感数据传输和存储需要加密。
- 遵循最小采集、最小权限和可撤回授权原则。
- 明确视频、音频、结构化事件和报告的保存周期及删除机制。
- 外部AI服务调用前应明确发送的数据范围并进行必要脱敏。

### 14.4 可解释与可审计

- 告警页面显示触发时间、场景、风险等级和可理解的触发依据。
- 后台保留输入摘要、规则/模型版本、状态流转和操作者记录。

### 14.5 婴幼儿交互安全

- 禁止未经验证的高频闪烁、高音量和持续刺激。
- 所有自动播放和灯光策略必须支持家长关闭和紧急中止。
- 涉及生理健康和人身安全的功能必须经过独立安全评审。

## 15. 验收计划

### 15.1 P0通用验收格式

每项P0需求必须包含：

- Given：用户、设备、网络、权限和数据所处状态。
- When：输入数据、操作或异常事件。
- Then：判断、告警、响应和记录结果。
- 指标：成功率、延迟、Precision、Recall或错误率。
- 证据：接口日志、数据库记录、消息回执、硬件回执、截图或测试报告。

### 15.2 T0.1必测用例

| 用例 | 核心验收结果 |
|---|---|
| 设备绑定闭环 | 账号、家庭、宝宝和设备关联正确，失败可恢复 |
| 设备离线 | 在线状态及时更新，实时结论停止且用户收到提示 |
| 熟睡规则 | 输入、规则版本、状态片段和时间线可追踪 |
| 哭闹三级规则 | 分级、去重、升级、自动响应授权及反馈均可验证 |
| 危险动作 | L3告警送达、人工确认、备用联系人升级和事件关闭完整 |
| 低置信度 | 不输出确定性结论，不执行高风险自动动作 |
| 告警失败 | 重试、备用渠道和失败记录生效 |
| 硬件响应 | 指令、执行回执、超时和失败提示一致 |
| 权限控制 | 未授权成员无法访问视频、告警和报告 |
| 报告生成 | 报告内容可回溯至事件，AI失败时可降级 |
| 24小时稳定性 | 形成起止时间、资源曲线、异常和恢复记录 |

### 15.3 发布门槛

T0.1进入下一阶段前，至少满足：

1. 三类核心场景的规则、测试样本和评估结果版本一致。
2. L2/L3告警具备真实送达和确认记录。
3. 高风险硬件响应不存在“接口返回成功即视为执行成功”的情况。
4. 设备离线、数据缺失、低置信度和告警失败均通过降级测试。
5. 24小时稳定性测试不存在未关闭的致命问题。
6. 生理及安全相关候选阈值完成专业和设备侧评审，或明确不进入发布范围。

## 19. 阶段结论

T0已经形成智能看护系统的主要产品框架和部分关键链路，但尚不能证明九类多模态识别、真实告警送达、真实硬件响应及量产级稳定性已经完成。

T0.1的合理策略是将范围收敛至熟睡、哭闹和危险动作三类场景，优先完成“有效感知—版本化判断—分级告警—人工/设备响应—结果沉淀”的可验证闭环。在形成真实样本、指标基线和端到端证据后，再决定是否扩展其余六类场景及多模态模型。

因此，本项目在作品集中的准确定位是：

> AIoT智能婴儿床T0工程验证与产品闭环搭建，以及基于现状审计提出的T0.1闭环验证方案。
